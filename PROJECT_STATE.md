# Remaining engineering limitations — 2026-10-10

- **Embedded tags:** Actual tag writing is intentionally limited to MP3 / ID3v2.3. Existing ID3v2.4 tags, unsupported global/frame flags, nonzero ID3v2.3 revisions, malformed/truncated tags, metadata tags above 2 MiB, and lyrics tags above 8 MiB fail closed rather than being rewritten. Real-file round-trips (especially APIC artwork, unusual flags, and large tags) have not been run.
- **Lyrics removal:** Saving embedded USLT lyrics is supported, but the delete action currently hides lyrics inside LogaRhythm and attempts to remove the companion `.lrc`; it does not remove an existing USLT frame. The UI explicitly warns that file copies may remain.
- **Storage compatibility:** Android 11+ uses single-item MediaStore consent for supported shared MP3 writes and track deletion. The Android 10 `RecoverableSecurityException` consent flow, SAF writes for arbitrary document providers, and grouped multi-file consent are not implemented. On Android 8–10, operations without an existing write grant fail honestly instead of bypassing security.
- **Consent lifecycle:** The pending approval callbacks live in the active Compose composition. If Android destroys that activity while the system consent screen is open, the pending operation may be dropped and must be initiated again; it does not silently perform an unapproved write.
- **MediaStore index:** MediaStore metadata columns such as title, artist, album, and genre are indexed/read-only on the platform. The app verifies embedded tags and updates Room, but other apps or a later MediaStore scan may not show the new indexed values immediately.
- **Companion LRC:** Companion-file access still depends on MediaStore exposing a usable filesystem path. Providers without an accessible `DATA` path cannot use this fallback; embedded MP3 writes use the content URI instead.
- **Recovery edge case:** If a provider partially writes a file and restoration cannot be verified, the original is retained under the app's `noBackupFilesDir` and logged. There is no in-app recovery UI for that exceptional backup.
- **Validation:** Only lightweight source/resource checks and a standalone JVM USLT payload round-trip smoke test were run. No Gradle compile, full JUnit/Robolectric suite, emulator/device test, real MediaStore permission test, broad MP3 corpus test, or performance benchmark was run.
- **Handoff:** The supplied snapshot has no Git history or Gradle wrapper launch scripts/JAR. Build configuration was left unchanged, and no APK was generated.
